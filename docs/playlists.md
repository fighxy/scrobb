## 0. Коротко

1. **Единого стандарта нет, есть три слоя.**
   - Локальные плееры понимают **M3U/M3U8**: путь к файлу и строка «Артист - Название».
   - Открытый структурный формат — **XSPF** и его JSON-форма **JSPF**. JSPF с расширениями MusicBrainz — родной формат плейлистов ListenBrainz.
   - Стриминги файлов не дают, только API. Переносчики (TuneMyMusic, Soundiiz) и Яндекс Музыка принимают **CSV** и **текстовый список**.
2. **Канонический формат Scrobb — JSPF**: ядро XSPF, расширение MusicBrainz и своё `https://scrobb.ru/jspf#track`. Через ListenBrainz или будущий сервер Scrobb такой плейлист уходит в Spotify и Apple Music.
3. **Остальные форматы — для совместимости:**
   - для плееров — **M3U8** и **XSPF**;
   - для переносчиков и Яндекс Музыки — **CSV** (колонки как у Exportify) и **TXT** («Артист - Название»);
   - **PLS** — только импорт.
4. **Трек в плейлисте — не ссылка на файл библиотеки.**
   - Хранится снимок метаданных, идентификаторы (MBID, ISRC, `ext_ids`) и путь на этом устройстве.
   - Поэтому плейлист переносим, а трек, которого нет в библиотеке, остаётся в плейлисте бледным и сам находится, когда файл появится.
5. **ISRC — главный ключ между стримингами.** Плеер читает его из тегов и кладёт в `ext_ids["isrc"]`: и в плейлисты, и в скробблы.
6. **Хранение — отдельная база `user.db` (SQLite).** Это правки пользователя, их нельзя пересобрать сканированием, в отличие от библиотеки.
   - **Порядок** — дробные ключи: вставка и перестановка не трогают соседей.
   - **Удаление** — надгробие.
   - **id** — UUIDv7.
7. **Синхронизация — через сервер Scrobb, правками по полям** (§7–§8).
   - У каждого поля — метка гибридных часов (HLC), побеждает поздняя; правки с разных устройств сливаются в любом порядке к одному результату.
   - Удаление окончательно, пути к файлам не синхронизируются.
   - Один запрос и отправляет изменённое, и забирает чужое после курсора.

## 1. Что принято у других

### 1.1 Локальные плееры и медиасерверы — M3U/M3U8

- **Кто:** foobar2000, AIMP, MusicBee, Winamp, VLC, Strawberry, Poweramp, Plex, Jellyfin, Navidrome.
  - Navidrome импортирует и экспортирует плейлисты командой `navidrome pls`.
  - Файлы `.m3u` из папок с музыкой Navidrome подхватывает при сканировании сам ([pls](https://www.navidrome.org/docs/usage/admin/cli/pls/)).
- **Формат** ([M3U](https://en.wikipedia.org/wiki/M3U)) — строка на запись: путь, относительный от папки плейлиста, абсолютный или URL. Расширенные директивы:

| Директива | Смысл | Как у нас |
|---|---|---|
| `#EXTM3U` | Заголовок, первая строка | Пишем; при чтении не обязателен |
| `#EXTINF:<сек>,<подпись>` | Длительность и «Артист - Название» следующей записи | Читаем и пишем. Хвост IPTV вроде `tvg-id="…"` пропускаем |
| `#PLAYLIST:` | Название плейлиста | Читаем и пишем |
| `#EXTALB:`, `#EXTART:` | Альбом и **артист альбома**, обычно один раз на список-альбом | Читаем, действуют на все записи после них. Артист альбома становится артистом трека, только если другого нет |

- **Кодировка.** Для `.m3u8` UTF-8 обязателен. Для `.m3u` берётся системная кодовая страница, поэтому старые AIMP и Winamp на русской Windows пишут **CP1251**.
  - Мы распознаём BOM UTF-8 и UTF-16.
  - Если файл не в UTF-8, читаем его как CP1251. Таблица своя, без `encoding_rs`: 64 символа для 0x80–0xBF, а «А»–«я» в 0xC0–0xFF идут подряд.
- **Ограничения.** Плейлист привязан к путям одного компьютера. Метаданных нет, кроме подписи. Poweramp `#EXTINF` вообще не пишет.

### 1.2 Открытый структурный — XSPF и JSPF

- **[XSPF](https://xspf.org/spec)** — XML-формат Xiph.
  - У трека есть `location` (URI), `identifier`, `title`, `creator`, `album`, `trackNum`, `duration` и расширения `<extension application="…">`.
  - Понимают VLC, Strawberry, Rhythmbox, Audacious.
- **[JSPF](https://musicbrainz.org/doc/jspf)** — тот же XSPF в JSON. MusicBrainz добавляет к нему расширения:
  - **плейлист** `https://musicbrainz.org/doc/jspf#playlist`: `creator`, `created_for`, `collaborators`, `copied_from`, `public`, `last_modified_at`, `additional_metadata`;
  - **трек** `https://musicbrainz.org/doc/jspf#track`: `added_by`, `added_at`, `artist_identifiers`, `release_identifier`, `additional_metadata`;
  - **запись MusicBrainz** — `identifier`: `https://musicbrainz.org/recording/<MBID>`.
- **ListenBrainz** хранит плейлисты в JSPF и отдаёт через [API](https://listenbrainz.readthedocs.io/en/latest/users/api/playlist.html). Эндпоинты:
  - `POST /1/playlist/create`;
  - `GET /1/playlist/(mbid)` и `/xspf`;
  - `item/add`, `item/move`, `item/delete`;
  - **экспорт в сервис:** `POST /1/playlist/(mbid)/export/(service)` и `POST /1/playlist/export-jspf/(service)` — второй экспортирует JSPF из тела запроса, без сохранения в ListenBrainz;
  - **импорт:** `GET /1/playlist/{spotify,apple_music,soundcloud}/(id)/tracks`.

  Это готовый открытый «мост» между стримингами, и он говорит на JSPF.

### 1.4 Выводы

- **Структурный формат — JSPF.** Он хранит всё, что нам нужно, совместим с ListenBrainz и расширяется без поломки чужих читателей.
- **Трек опознаётся по идентификаторам и метаданным, а не по пути.** Порядок:
  1. MBID — в мире MusicBrainz и ListenBrainz;
  2. ISRC — в стримингах;
  3. «артист + название» с нормализацией — везде.

  Путь работает только на своём компьютере.
- **M3U8, CSV и TXT нужны, потому что их принимают другие.** Источником истины они быть не могут: теряют метаданные.

## 2. Форматы в Scrobb

| Формат | Импорт | Экспорт | Для кого | Что сохраняется |
|---|---|---|---|---|
| **M3U / M3U8** | ✓ | ✓ (`.m3u8`, UTF-8) | Любой плеер, Navidrome, Poweramp | Путь, длительность, «Артист - Название». Треки без файла на этом компьютере не попадают в файл, о чём говорит уведомление |
| **XSPF** | ✓ | ✓ | VLC, Strawberry, Rhythmbox, Soundiiz | Плюс `file://`-URI с процентным кодированием, альбом, MBID в `identifier` |
| **JSPF** | ✓ | ✓ | ListenBrainz, Scrobb, перенос между нашими устройствами | Всё: артисты списком, артист альбома, `ext_ids` (ISRC, Spotify и др.), время добавления, id плейлиста |
| **CSV** | ✓ | ✓ | TuneMyMusic, Soundiiz, Excel, Exportify | Название, артисты, альбом, артист альбома, длительность, ISRC, MBID, путь. Импорт узнаёт колонки по названиям, в том числе русским; разделитель `,`, `;` (Excel) или таб; кавычки по RFC 4180 |
| **TXT** | ✓ | ✓ | Импорт Яндекс Музыки, переносчики | Только «Артист - Название». При импорте разделители ` - `, ` — `, ` – `, нумерация «1.» отрезается |
| **PLS** | ✓ | — | Старые плееры, радио | Путь, название, длительность |

**Формат файла определяется по расширению.** CSV — по `.csv` и `.tsv`. Если расширение незнакомое, формат определяется по началу файла:
- `#EXTM3U` — M3U;
- `[playlist]` — PLS;
- `<?xml` или `<playlist` — XSPF;
- `{` — JSPF;
- иначе — текстовый список.

**Пример JSPF Scrobb** (сокращён):

```json
{ "playlist": {
    "title": "Вечер на кухне",
    "annotation": "Тихое на вечер",
    "date": "2026-10-25T09:00:00Z",
    "extension": {
      "https://musicbrainz.org/doc/jspf#playlist": { "public": false, "last_modified_at": "2026-10-25T09:30:00Z" },
      "https://scrobb.ru/jspf#playlist": { "id": "01a17274-6494-7616-a03b-7020ff4144ee" } },
    "track": [ {
      "title": "Кукушка", "creator": "Кино", "album": "Чёрный альбом", "duration": 397000,
      "identifier": ["https://musicbrainz.org/recording/<MBID>"],
      "location": ["file:///home/ivan/%D0%9C%D1%83%D0%B7%D1%8B%D0%BA%D0%B0/Kino/kukushka.flac"],
      "extension": {
        "https://musicbrainz.org/doc/jspf#track": { "added_at": "2026-10-25T09:05:00Z" },
        "https://scrobb.ru/jspf#track": { "artists": ["Кино"], "album_artist": "Кино", "ext_ids": { "isrc": "RUA018700012" } } } } ] } }
```

Чужой читатель увидит обычный JSPF, ListenBrainz — свои поля, а Scrobb восстановит плейлист без потерь. При чтении строки и массивы в `identifier`, `location` и `creator` принимаются в любой форме: разные программы пишут по-разному.

## 3. Модель данных

```
Playlist     { id: UUIDv7, title, description?, origin?, created_at_ms, updated_at_ms }
PlaylistItem { id: UUIDv7, position: ключ порядка, added_at_ms,
               location?: путь на этом устройстве,
               track: TrackSnapshot { title, artists[], album?, album_artist?, duration_ms?,
                                      recording_mbid?, ext_ids{isrc, spotify, …} } }
```

- **`TrackSnapshot`** — тот же снимок, что в истории прослушиваний ([player-history.md](player-history.md) §3), теперь он в `player-domain`.
  - Снимок не обновляется вслед за тегами: плейлист помнит, что в него положили.
  - Что сейчас играет, решает поиск по библиотеке (§4).
- **`origin`** показывает, откуда плейлист: `null` — создан в плеере, `import:m3u`, `import:jspf` и т. д.
- **Порядок.** `position` — дробный ключ в base-62 (`0-9A-Za-z`, никогда не оканчивается на `0`).
  - `between(a, b)` даёт ключ строго между соседями, `spread(a, b, n)` — n ключей для вставки пачки.
  - Перестановка меняет одну строку, поэтому правки с двух устройств сливаются без перенумерации.
  - При равных ключах (одновременная вставка на двух устройствах) порядок решает `id`. На этот случай индекс `(playlist_id, position, id)`.
- **Удаление** — надгробие `deleted_at_ms`: синхронизации нужно знать, что элемент удалён, а не «ещё не пришёл».
- **Метки правок.** У полей, которые правят пользователи, — метка гибридных часов: `title_hlc`, `description_hlc`, `position_hlc`, `deleted_hlc` (§7.1).
  - Неотправленное отмечено номером правки: `change_no > pushed_no`.
  - Узел часов и курсор сервера хранятся в `sync_state`.
- **Хранилище** — трейт `PlaylistStore`. Детерминированный: id, время и позиции приходят от вызывающего, поэтому тесты воспроизводимы.
  - `MemoryPlaylists` — для тестов и как образец.
  - `SqlitePlaylists` — `user.db`, таблицы `STRICT`, WAL, миграции по `user_version`. Как в `history.db`, базу более новой версии ядро не открывает.

  Обе реализации проходят общий набор `player-testkit::playlists::conformance`.

```sql
CREATE TABLE playlists (id TEXT PRIMARY KEY, title TEXT NOT NULL, description TEXT, origin TEXT,
  created_at_ms INTEGER NOT NULL, updated_at_ms INTEGER NOT NULL, deleted_at_ms INTEGER) STRICT;
CREATE TABLE playlist_items (id TEXT PRIMARY KEY, playlist_id TEXT NOT NULL REFERENCES playlists (id),
  position TEXT NOT NULL, added_at_ms INTEGER NOT NULL, location TEXT,
  title TEXT NOT NULL, artists TEXT NOT NULL /* JSON */, album TEXT, album_artist TEXT,
  duration_ms INTEGER, recording_mbid TEXT, ext_ids TEXT NOT NULL DEFAULT '{}', deleted_at_ms INTEGER) STRICT;
CREATE INDEX playlist_items_order ON playlist_items (playlist_id, position, id) WHERE deleted_at_ms IS NULL;
-- v2: синхронизация (§7); колонки добавляются по одной
ALTER TABLE playlists ADD COLUMN title_hlc, description_hlc TEXT NOT NULL; deleted_hlc TEXT;
  change_no, pushed_no INTEGER NOT NULL DEFAULT 0;
ALTER TABLE playlist_items ADD COLUMN position_hlc TEXT NOT NULL; deleted_hlc TEXT; change_no; pushed_no;
CREATE TABLE sync_state (id INTEGER PRIMARY KEY CHECK (id = 1), node INTEGER, cursor TEXT,
  change_seq INTEGER NOT NULL) STRICT;
```

При переходе на v2 сохранённые раньше плейлисты получают метки из своего времени с узлом 0. Все они становятся неотправленными и уйдут на сервер при первой синхронизации.

**Почему отдельный `user.db`.** Библиотека — кэш файлов: её можно удалить и пересканировать. История и правки пользователя невосполнимы. Там же — состояние синхронизации (§7), позже — рейтинги и «любимые».

## 4. Как трек плейлиста находится в библиотеке

`player-library::LibraryIndex` ведётся при каждом добавлении и удалении трека. Запрос — `TrackQuery { location, track }`, порядок поиска:

1. **Путь**: сначала точное совпадение, затем без учёта регистра и вида разделителей `\` и `/` — плейлисты с Windows.
2. **MBID записи.**
3. **ISRC.** Читается из тегов (`ItemKey::Isrc`) и хранится без дефисов, в верхнем регистре.
4. **Ключ «артист + название»** — `scrobb-sync::TrackKey`, нормализация как у сервера:
   - NFKC;
   - «ё» → «е»;
   - пробелы схлопнуты;
   - casefold;
   - из названия убрано «(feat. …)», «ft.», «при участии»;
   - артист — главный, до `feat.`/`ft.`/`featuring`/`при уч.`/`при участии`. Знак `&` и запятая артиста не делят: «Simon & Garfunkel» — один артист.

   Векторы — в [`contracts/match-key/v1.json`](../contracts/match-key/v1.json), их проходит ядро плеера, позже бэкенд.

Если кандидатов несколько, выигрывает тот же альбом, затем ближайшая длительность. Если обе длительности известны и расходятся больше чем на 10 с, это другая запись: живая версия или ремикс.

Поиск идёт при каждом открытии плейлиста, а не при импорте. Поэтому трек, которого не было, находится сам, как только папка просканирована. Плеер проверен на M3U8 c путём `D:\Музыка\…mp3` и подписью «КИНО feat. Кто-то - Спокойная Ночь»: трек нашёлся по ключу.

## 5. Импорт и экспорт

- **Импорт** — `Core::import_playlist(file_name, bytes, base_dir)`:
  - определяет формат и кодировку;
  - превращает относительные пути в абсолютные от папки файла (`..`, `\`, `file://`-URI с процентами);
  - дополняет снимок данными из библиотеки, если трек нашёлся (пустые поля — из тегов, заполненные остаются из файла);
  - создаёт плейлист и отдаёт отчёт `{ playlist, total, matched }`.

  В десктопе импорт вызывают из меню и из «Открыть с помощью» для `.m3u`, `.m3u8`, `.pls`, `.xspf`, `.jspf` — тогда окно сразу открывает плейлист. CSV и TXT импортируются только через меню: по расширению их не отличить от таблиц и заметок.
- **Экспорт** — `Core::export_playlist(id, format, target_dir)`:
  - берёт путь из библиотеки, если трек нашёлся;
  - пишет пути в M3U8 относительно папки файла, если у них общая папка, иначе абсолютными;
  - отдаёт текст и число треков, которые не попали в M3U8 без пути. Файл пишет оболочка.

## 6. Интерфейс десктопа

- **Слева** — «Плейлисты | Папки». В списке плейлистов — мозаика обложек до 4 альбомов, кнопки «Импорт» и «Создать».
- **Экран плейлиста:**
  - шапка: название, описание, «N треков · длительность · K нет в библиотеке»;
  - «Играть» — в очередь попадают только найденные треки;
  - «Экспорт» с подсказкой, какой формат для чего, и «⋯» с пунктами «Название и описание» и «Удалить».
- **Добавить в плейлист** — из меню трека, шапки альбома и артиста, панели «Сейчас играет» или перетаскиванием трека на плейлист слева.
- **Порядок** меняется перетаскиванием строк, а с клавиатуры — пунктами меню «Выше» и «Ниже».
- **Поиск ⌘K** находит и плейлисты.
- **Синхронизация** — значок облака рядом с «Плейлисты | Папки».
  - В подсказке — состояние: «синхронизированы 2 мин назад», «нет связи — правки уйдут позже», «сервер пока не умеет», «подключите Scrobb».
  - Щелчок — синхронизировать сейчас; если устройство не привязано — привязать.
  - То же состояние — строкой в меню Scrobb.
  - Окно, вернувшееся на экран, синхронизируется само, но не чаще раза в 15 секунд.

## 7. Синхронизация между устройствами

Клиентская часть сделана: ядро плеера, десктоп, тесты на эталонном сервере. На реальных устройствах синхронизация заработает, когда сервер Scrobb реализует эндпоинт из §8. До тех пор плеер получает `404`, показывает «сервер пока не умеет» и хранит правки; они уйдут при первой удачной синхронизации.

### 7.1 Что синхронизируется и как сливается

Состояние — набор записей: плейлисты и элементы. У каждого изменяемого поля своя метка времени правки (гибридные логические часы, HLC):

| Запись | Неизменное с создания | «Последняя запись побеждает» | Надгробие |
|---|---|---|---|
| Плейлист | `id`, `created_at_ms`, `origin` | `title`, `description` — каждое отдельно | `deleted` |
| Элемент | `id`, `playlist_id`, `added_at_ms`, `track` (снимок) | `position` (ключ порядка) | `deleted` |

- **Метка HLC** — строка `<мс Unix, 13 цифр>-<счётчик, 10 цифр>-<узел, 8 hex>`, например `1761384000000-0000000002-1a2b3c4d`.
  - Ширина постоянная, поэтому строки сравниваются так же, как метки.
  - Устройство берёт метку не меньше всех, что видело. Поэтому правка, сделанная после синхронизации, побеждает пришедшие, даже если системные часы устройства отстают.
  - Узел — случайное число устройства, не 0. Узел 0 — у плейлистов, сохранённых до синхронизации.
- **Слияние** двух версий одной записи:
  - каждое поле «последняя запись побеждает» берётся с большей меткой; при равных метках — с большим значением;
  - `created_at_ms` и `added_at_ms` — меньшее, `origin` — большее (`null` меньше строки);
  - `deleted` — большая метка.

  Слияние коммутативно, ассоциативно и идемпотентно: порядок прихода и повторы не важны. Правила закреплены векторами [`contracts/playlist-sync/v1.json`](../contracts/playlist-sync/v1.json) — их проходит ядро плеера, должен проходить и сервер.
- **Поля независимы.** Переименование на одном устройстве и смена описания на другом сохраняются обе. Перестановки разных треков применяются обе, одного трека — побеждает поздняя.
- **Удаление окончательно.** Удалённый плейлист не возвращается правкой с устройства, которое об удалении ещё не знало, а убранный трек — перестановкой.
  - Цена: правки офлайн-устройства в удалённом плейлисте теряются.
  - Зато удалённое не воскресает.
- **Не синхронизируются:**
  - **путь к файлу** — он свой на каждом устройстве. На другом устройстве трек ищется по MBID, ISRC и ключу «артист + название» (§4), а файлы на сервер не уходят даже путями;
  - **локальные id треков библиотеки.**
- Один и тот же файл, импортированный на двух устройствах, даст два плейлиста: id создаёт устройство.

### 7.2 Что делает плеер

- **Хранение** — `user.db` v2 (§3).
  - Правка ставит метку только тем полям, что изменились: сохранение диалога без изменений не затирает переименование с другого устройства.
  - Пришедшее с сервера не становится неотправленным.
- **Когда синхронизирует:**
  - через 1,5 с после правки — несколько правок подряд уходят одним запросом;
  - раз в минуту;
  - когда окно возвращается на экран, но не чаще раза в 15 с;
  - по щелчку на значок;
  - после привязки к аккаунту. Тогда — заново: курсор забыт, всё местное отправляется, всё серверное принимается. Так плейлисты попадают и в другой аккаунт.
- **Обмен** — `POST /api/v1/sync/playlists`, пока есть что отправить или получить:
  - в запросе все неотправленные плейлисты, до 500 неотправленных элементов и курсор;
  - ответ сливается одной транзакцией;
  - отметка «отправлено» снимается только с записей, не менявшихся во время запроса;
  - курсор запоминается после слияния. Сбой посередине — повтор той же пачки, а слияние идемпотентно.
- **Ошибки:**
  - нет сети, `5xx`, `429` — повтор с паузой (`scrobb_client::retry::Backoff`), правки копятся;
  - `401` и `426` останавливают и синхронизацию, и скробблы до новой привязки или обновления;
  - `404` — «сервер пока не умеет», повтор через час.
- **Окну** приходят события `playlist_sync` (состояние и время последнего обмена) и `playlists_changed` (пришли чужие правки — перечитать).

### 7.3 Как проверено

- **Векторы** `playlist-sync/v1` — каждый случай во всех порядках слияния, плюс повторное слияние. Формат HLC — отдельными векторами.
- **Общие проверки хранилищ** — память и SQLite одинаково. Проверяются:
  - неотправленное и метки по полям;
  - правка во время запроса остаётся неотправленной;
  - слияние пришедшего, своя неотправленная правка против старой и новой чужой;
  - элемент без плейлиста — ошибка без частичного применения;
  - узел, курсор, сброс;
  - переход базы v1 → v2.
- **Два ядра с эталонным сервером в памяти** (`player-testkit::server`). Часы «телефона» отстают на 5 минут. Проверяются:
  - перенос с поиском файлов в другой библиотеке;
  - одновременные правки разных полей и порядка;
  - переименование после синхронизации на отстающих часах побеждает;
  - удаление против офлайн-правок;
  - отправка сама после правки и приём раз в минуту;
  - 620 элементов пачками в обе стороны, в том числе сервер без возврата присланного и страницы по 50;
  - `404`, `503`, нет сети, `401`;
  - привязка к другому аккаунту;
  - SQLite после перезапуска с отставшими часами.
- **Мутации** — каждая из 12 намеренных поломок роняет тесты:
  - нет догоняния часов при запуске и перед слиянием;
  - метка неизменённому полю, в памяти и в SQLite;
  - удаление не окончательно;
  - отметка «отправлено» без номера правки;
  - нет продолжения при полной пачке;
  - сервер не прикладывает плейлисты к элементам;
  - `404` без паузы;
  - привязка без начала заново;
  - пришедшее становится неотправленным;
  - ветка счётчика HLC.
- **Два собранных приложения под Xvfb** — каждое со своими данными и хранилищем секретов, сервер — dev-сервер (§8.5):
  - привязка через значок синхронизации;
  - импортированный на первом `.m3u8` появился на втором, треки нашлись в его библиотеке и сыграли;
  - перестановка на втором дошла до первого.

## 8. Сервер Scrobb: эндпоинт синхронизации (спецификация для бэкенда)

[architecture.md](architecture.md) §9.6 говорил «плейлисты не делаем». Плеер это меняет: плейлисты нужны для синхронизации и переноса. Ниже — то, что ждёт клиент. Эталон в коде — `player/core/crates/player-testkit/src/server.rs`; правила слияния — контракт `playlist-sync/v1`.

### 8.1 `POST /api/v1/sync/playlists`

Авторизация — токен устройства (`Authorization: Bearer scr_…`), как у `/api/v1/scrobble/listens`. Тело и ответ — JSON.

```json
{
  "cursor": "1824",
  "limit": 500,
  "playlists": [
    { "id": "01a17274-6494-7616-a03b-7020ff4144ee", "created_at_ms": 1761381065000, "origin": "import:m3u",
      "title":       { "value": "Дорога", "stamp": "1761384000000-0000000000-1a2b3c4d" },
      "description": { "value": null,     "stamp": "1761381065000-0000000000-1a2b3c4d" } }
  ],
  "items": [
    { "id": "01a17274-64a1-7c3e-9a51-3f0a8e2c1b77", "playlist_id": "01a17274-6494-7616-a03b-7020ff4144ee",
      "added_at_ms": 1761381065000,
      "track": { "title": "Кукушка", "artists": ["Кино"], "album": "Чёрный альбом", "album_artist": "Кино",
                 "duration_ms": 397000, "recording_mbid": null, "ext_ids": { "isrc": "RUA018700012" } },
      "position": { "value": "V", "stamp": "1761381065000-0000000001-1a2b3c4d" },
      "deleted": "1761384100000-0000000000-1a2b3c4d" }
  ]
}
```

- **`cursor`** — из прошлого ответа; `null` — с начала.
- **`limit`** — сколько записей клиент готов принять; клиент шлёт 500.
- **`playlists`, `items`** — изменённое на устройстве, в окончательном виде записи. Плейлисты идут раньше элементов. Записей в одном запросе — до 500 элементов и все изменённые плейлисты.
- **Поля:** `origin` и `deleted` без значения опускаются; `track` — снимок трека, тот же, что в скробблах.

Ответ `200`:

```json
{ "cursor": "1830", "more": false, "playlists": [ … ], "items": [ … ] }
```

- **`playlists`, `items`** — записи, изменённые после курсора запроса, в окончательном виде: уже слитые с присланным.
- **`cursor`** — для следующего запроса.
- **`more: true`** — есть ещё, клиент сразу повторит запрос с новым курсором.

### 8.2 Что делает сервер

1. **Одна транзакция на запрос.** Каждую присланную запись — сначала плейлисты, потом элементы — слить с хранимой по правилам §7.1.
   - Новая или изменившаяся запись получает следующий номер изменения пользователя (`seq`, растёт на аккаунт).
   - Неизменившаяся номер не меняет: повтор запроса ничего не сдвигает.
2. **Элемент неизвестного плейлиста** принять и сохранить: плейлист может прийти следующим запросом.
3. **Ответ:**
   - записи с `seq` больше курсора (`null` — 0), по возрастанию `seq`, не больше `min(limit, предел сервера)`;
   - к каждому элементу в ответе — запись его плейлиста, даже если тот не менялся: клиенту нужен плейлист раньше элемента;
   - `cursor` — `seq` последней отданной записи, а если отдавать нечего — курсор запроса;
   - `more` — остались ли записи после него.
4. **Присланное этим же запросом** сервер может не возвращать: клиент сам продолжает, пока у него есть неотправленное. Может и возвращать — клиент сольёт без изменений.
5. **Сравнение меток в SQL — побайтно.** В Postgres — `COLLATE "C"`: в языковых сопоставлениях `-` и регистр hex могут сравниваться иначе. Значения при равных метках сравниваются по кодовым точкам, как `str` в Python и `String` в Rust.
6. **Коды ответа:**

   | Код | Когда |
   |---|---|
   | `400` | Тело не разобралось |
   | `401` | Токен отозван |
   | `413` | Больше 500 элементов |
   | `426` | Версия клиента ниже минимальной |
   | `429` | С `Retry-After` |
   | `5xx` | Сбой сервера: клиент повторит |

   `404` клиент понимает как «сервер синхронизацию не умеет».
7. **Сопоставление трека элемента** с каталогом (`track_id` через `external_ids` и `match_key`, [architecture.md](architecture.md) §5.3) — дело сервера для веба и статистики. Синхронизация от него не зависит: клиенту возвращается снимок как прислан.

### 8.3 Эскиз таблиц (Postgres)

```sql
ALTER TABLE users ADD COLUMN playlist_seq bigint NOT NULL DEFAULT 0;  -- счётчик изменений: UPDATE … RETURNING

CREATE TABLE playlists (
  user_id         bigint NOT NULL REFERENCES users,
  id              uuid   NOT NULL,                 -- задаёт устройство (UUIDv7)
  created_at      timestamptz NOT NULL,
  origin          text,
  title           text NOT NULL,
  title_hlc       text COLLATE "C" NOT NULL,
  description     text,
  description_hlc text COLLATE "C" NOT NULL,
  deleted_hlc     text COLLATE "C",               -- надгробие; удаление окончательно
  public          boolean NOT NULL DEFAULT false,  -- для веба и §8.4
  seq             bigint NOT NULL,
  PRIMARY KEY (user_id, id)
);
CREATE INDEX ON playlists (user_id, seq);

CREATE TABLE playlist_items (
  user_id      bigint NOT NULL REFERENCES users,
  id           uuid   NOT NULL,
  playlist_id  uuid   NOT NULL,                    -- без внешнего ключа: элемент может прийти раньше плейлиста
  added_at     timestamptz NOT NULL,
  track        jsonb  NOT NULL,                    -- снимок как прислан
  track_id     bigint REFERENCES tracks,           -- сопоставление (§5.3), может быть NULL
  position     text COLLATE "C" NOT NULL,          -- дробный ключ порядка
  position_hlc text COLLATE "C" NOT NULL,
  deleted_hlc  text COLLATE "C",
  seq          bigint NOT NULL,
  PRIMARY KEY (user_id, id)
);
CREATE INDEX ON playlist_items (user_id, seq);
```

`seq` у плейлистов и элементов общий на пользователя: ответ собирается слиянием двух выборок по `seq > cursor`.

### 8.4 Дальше на сервере

1. **API в JSPF, совместимый с ListenBrainz `/1/playlist/*`:**
   - `create`, `GET (id)`, `edit`;
   - `item/add`, `item/move`, `item/delete`;
   - `delete`.

   Он работает поверх тех же таблиц. Сторонние клиенты, которые умеют ListenBrainz, получают плейлисты бесплатно — так уже работает приём скробблов (§3.2).
2. **Экспорт в сервисы — с сервера, а не из каждого клиента:**
   - **Spotify, Apple Music** — пока у Scrobb нет Extended Quota (§1.3), через `POST /1/playlist/export-jspf/(service)` ListenBrainz, от имени пользователя, который привязал там свой Spotify. Позже — свой OAuth.
   - **Яндекс Музыка** — TXT для страницы импорта; прямой путь появится вместе с её API.
   - **Остальные** — CSV для переносчиков.
3. **Веб-приложение** показывает и правит те же плейлисты, профиль получает вкладку «Плейлисты». Правки веба — те же записи с метками.

### 8.5 Dev-сервер для разработки

`cargo run -p player-testkit --example scrobb-dev-server -- --port 8787` — эталонный сервер по HTTP:
- привязка подтверждается сразу;
- скробблы принимаются;
- плейлисты синхронизируются;
- всё хранится в памяти.

Плеер запускается с `SCROBB_BASE_URL=http://127.0.0.1:8787`.

## 9. Что дальше

- **Умные плейлисты** — правила поверх библиотеки и истории. Отложены по решению Ивана, модель их не задевает: это другой `origin` и запрос вместо элементов.
- **Прямые интеграции** — после сервера (§8.4).
- **Обложка плейлиста** — своя картинка вместо мозаики.
- **«Найти недостающие»** — подсказать, в какой папке может быть трек, или открыть его в стриминге по ISRC.
