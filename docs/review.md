> Статус: **ревью** от 07.10.2026 по документам [README](../README.md), [architecture.md](architecture.md), [stack-rationale.md](stack-rationale.md), [music-services-ru.md](music-services-ru.md) и [ci-cd.md](ci-cd.md). Правки по технологиям и версиям (§2, пп. 1–4) уже внесены в документы, остальное — список того, что решить или сделать. Пометка **(не проверено)** — как в остальных документах.

## Итог

Проработка сильная. Решения обоснованы, ограничения (152-ФЗ, 149-ФЗ, ToS Last.fm) учтены с самого начала, запись идемпотентна, очередь и почта спрятаны за тонкими интерфейсами, непроверенное честно помечено.

Перед первым кодом стоит закрыть три вещи:

1. MVP слишком широк для 1–2 человек.
2. Несколько непроверенных допущений могут перевернуть ключевые решения — их надо проверить до кода (§1).
3. В документах есть пробелы и противоречия, которые всплывут в первые же недели (§3).

## 1. Главные риски: проверить до первого кода

1. **Объём MVP.** В [architecture.md](architecture.md), §14, двенадцать пунктов: три протокола приёма, своё расширение для двух семейств браузеров с 4–5 коннекторами и публикацией в магазинах, импорт Last.fm через egress-узел, статистика, стрики, достижения с выдачей задним числом, подписки и лидерборды, Telegram-бот, почта с обработкой bounce, донаты. Для 1–2 человек это много месяцев до первого пользователя. Вариант порядка — §4.
2. **Мобильные — главный продуктовый пробел.** Скорее всего, большую часть Яндекс Музыки и VK слушают с телефона; это стоит проверить данными. На этапе 1 у таких пользователей есть только Pano Scrobbler на Android с ручным токеном, на iOS — ничего. Для стриков это критично: день слушал только с телефона — стрик сгорел. Что делать:
   - оценить долю мобильного прослушивания;
   - поставить свой Android-скробблер (через медиасессии, RuStore + APK) раньше десктопа;
   - рассмотреть Ynison как опциональный экспериментальный провайдер. Это единственный путь для iOS и колонок; риск по ToS уже описан в [music-services-ru.md](music-services-ru.md), §4.
3. **Магазины расширений.** Решение «своё расширение — основной путь» держится на непроверенном [architecture.md](architecture.md), §18.11. Взнос Chrome Web Store российской картой, скорее всего, не оплатить (**не проверено**). Это надо проверить первым. Запасные каналы:
   - каталог Opera (из него ставит Яндекс Браузер), Firefox AMO, Edge Add-ons;
   - предложить в Web Scrobbler отдельный сервис «Scrobb», как там уже есть Maloja и ListenBrainz. Тогда расширение будет в магазинах без собственной публикации.
4. **Импорт Last.fm в задуманном виде из РФ почти не работает.**
   - Для привязки через web auth ([architecture.md](architecture.md), §4.1) пользователь открывает last.fm в своём браузере, а сайт из РФ закрыт (R1). Без VPN привязка не пройдёт.
   - Egress-узел обходит гео-блокировку, которую Last.fm ввёл сам. Это стоит прямо описать в письме partners@last.fm.
   - Что добавить: импорт по username без подтверждения владения (такие данные не участвуют в общих рейтингах) и импорт из файлов — экспорт ListenBrainz (данные CC0), Spotify Extended Streaming History, CSV популярных экспортёров Last.fm.
5. **152-ФЗ, ст. 10.1.** Публичный профиль с историей прослушиваний — это распространение ПДн, для него нужно отдельное согласие с возможностью задать запреты. В документах этого нет ([architecture.md](architecture.md), §8.3, §15). От ответа зависят онбординг и видимость профиля по умолчанию. Вопрос юристу — вместе с §16, п. 9. Туда же: минимальный возраст пользователей и тексты интерфейса без советов «включите обход блокировки».
6. **Telegram.** С 2025 года РКН ограничивает функции Telegram. Если станет хуже, вебхук и рассылки с VPS в РФ перестанут работать. Бот не должен быть критичным путём; как второй канал можно рассмотреть MAX — условия для ботов нужно проверить.

## 2. Технические решения, которые стоит пересмотреть сейчас

1. **Python 3.12 и PostgreSQL 16 в октябре 2026.** Python 3.12 и 3.13 получают только исправления безопасности, исправления ошибок идут только в 3.14; 3.15 выходит в октябре 2026, и колёса зависимостей под неё появятся не сразу ([devguide](https://devguide.python.org/versions/)). В PostgreSQL 18 (25.09.2025) есть skip scan по составным B-tree индексам, асинхронный I/O и встроенный `uuidv7()` ([анонс](https://www.postgresql.org/about/news/postgresql-18-released-3142/)); в Yandex Managed Service for PostgreSQL версия 18 уже доступна ([docs](https://yandex.cloud/en/docs/managed-postgresql/)).
   → **Внесено:** Python 3.14, PostgreSQL 18 (запасной вариант — 17), Valkey 9 — README, [architecture.md](architecture.md) §6.1, [stack-rationale.md](stack-rationale.md), [ci-cd.md](ci-cd.md).
2. **Очередь — выбрать сейчас, а не «до продакшена».** arq с 18.10.2025 в режиме maintenance-only, и писать адаптер под него, чтобы потом менять, — двойная работа. procrastinate (очередь в PostgreSQL, релиз 3.10.0 от 23.09.2026) умеет блокировки на задачу, приоритеты, повторы, периодические задачи без отдельного планировщика и постановку задачи в транзакции приложения ([docs](https://procrastinate.readthedocs.io/en/stable/reference.html)).
   → **Внесено:** очередь — procrastinate за интерфейсом `jobs`; SQLAlchemy на драйвере psycopg 3 (общем с очередью); outbox — постановка задачи-события в той же транзакции, без своей таблицы и диспетчера; процесса `scheduler` больше нет; Valkey — один экземпляр (кэш), без экземпляра с `noeviction` и AOF. Работу на нашей связке — **не проверено**, это первый спайк ([architecture.md](architecture.md), §6.3, §16, п. 47).
3. **Обогащение через API MusicBrainz не успеет.** По оценке [architecture.md](architecture.md), §7.3, у 1 000 пользователей 1–2 млн уникальных алиасов. При лимите 1 запрос в секунду это 12–23 дня очереди. Русскоязычный каталог в MusicBrainz покрыт слабо, поэтому длительность и обложки стоит брать и от своих клиентов. Важно: теги и жанровые метки MusicBrainz — не CC0, а supplementary data под CC BY-NC-SA 3.0 ([MusicBrainz Database](https://musicbrainz.org/doc/MusicBrainz_Database)), а ежечасная репликация бесплатна только для некоммерческого использования.
   → **Внесено:** основной справочник — локальная выборка core-данных MusicBrainz (CC0) из дампа в схеме `mb`, API — только для того, что новее дампа; вопросы о размере копии и о коммерческом использовании (Pro) — [architecture.md](architecture.md), §6.1, §16, пп. 45–46.
4. **pg_partman.** В CI стоял образ `postgres:16`, а в официальном образе pg_partman нет — `alembic upgrade head` упал бы. Наличие расширения у managed-провайдеров тоже не проверено.
   → **Внесено:** секции создаёт своя периодическая задача `partitions.ensure`: месячные — с года запуска и на 3 месяца вперёд, годовые — для исторических импортов ([architecture.md](architecture.md), §2.3; [ci-cd.md](ci-cd.md), §6.6).
5. **Нормализация `match_key` — контракт, который после запуска менять нельзя.** `alias_id` входит в первичный ключ `listens`. Если поменять нормализацию, повторная отправка того же скроббла (офлайн-очередь, повторный импорт) даст дубль. Нормализацию нужно зафиксировать golden-тестами на реальных русских метаданных и версионировать. Сейчас код противоречит тексту ([architecture.md](architecture.md), §2.4): `match_key()` делит артиста по `&`, `,` и `x`, а текст под ним говорит, что в MVP отрезается только `feat./ft.`.
   → Не внесено: это решение по модели данных.
6. **Гонка в дедупликации между источниками** ([architecture.md](architecture.md), §5.4). Два одновременных запроса одного пользователя (расширение и синхронизация) оба пройдут проверку по окну времени. Лечится блокировкой `pg_advisory_xact_lock(user_id)` на время записи.
   → Не внесено.

## 3. Пробелы и противоречия в документах

- **В DDL `listens`** ([architecture.md](architecture.md), §2.3) нет полей, на которые ссылаются другие разделы: `additional_info` с коннектором (§18.3), `submission_client` и `music_service` (§9.3). Надо решить, что хранится на каждое прослушивание (например, `client_id smallint` со справочником), и пересчитать объём в §7.3.
- **Альбом прослушивания.** Matcher сопоставляет только пару «артист, трек», а откуда берётся `listens.album_id`, не описано. От этого зависит точность топа альбомов: синглы, сборники.
- **Расписания в CI.** Ночные e2e коннекторов ([architecture.md](architecture.md), §18.12) и ежемесячная проверка восстановления «в CI по расписанию» (§7.2) противоречат [ci-cd.md](ci-cd.md): расписаний нет (§2), данных prod в CI нет (§6.5). Проверку восстановления лучше делать cron'ом на сервере в РФ, e2e — на self-hosted раннере.
- **Бюджет минут CI** ([ci-cd.md](ci-cd.md), §4) не учитывает сборку расширения на каждый PR и сборку десктопа. Windows-минуты расходуют квоту с множителем (по документации GitHub ×2, macOS ×10; сверить).
- **Админка** упоминается несколько раз (перезапуск задач, слияние треков, рассылки), но не спроектирована. В MVP она нужна для:
  - dead-letter и перезапуска задач;
  - слияния треков и артистов;
  - переименования @username;
  - модерации аватаров и «о себе»;
  - блокировки токенов.

  Вход в неё — отдельный, с 2FA и журналом действий.

## 4. Что добавить к старту

**Порядок работ.** Это смена очерёдности, а не отказ от принятых решений:

0. **Проверки, 1–2 недели:**
   - магазины расширений;
   - Last.fm API и web auth из РФ;
   - юрист: ИП или НПД, вход по email и паролю (149-ФЗ), ст. 10.1, egress-узел, ПДн в Telegram;
   - хостинг: PostgreSQL 18 у выбранного провайдера, S3, цена;
   - спайк очереди: procrastinate + SQLAlchemy async + psycopg 3 с постановкой задачи в транзакции приложения;
   - коннекторы Яндекс Музыки, VK и Звука на текущей вёрстке сайтов.
1. **Закрытая альфа:**
   - вход через VK ID и Яндекс ID;
   - ListenBrainz-совместимый приём и API-токены — сразу заработают Web Scrobbler, Pano Scrobbler и Navidrome;
   - история, топы, график по дням, стрик;
   - импорт по username и из файлов;
   - без бота, почты, донатов и достижений.
2. **Бета:**
   - своё расширение и привязка устройства (родной API — тонкий слой над тем же `IngestService`);
   - подписки, приватность, дружеские лидерборды;
   - достижения.
3. **Публичный запуск:**
   - Telegram-бот;
   - минимальная почта: только транзакционные письма, bounce и suppression — когда появятся рассылки;
   - донаты;
   - эндпоинт `/2.0/`.

**Инженерный минимум до первого PR:**

- монорепозиторий (backend, web, extension) с общим OpenAPI-клиентом и проверкой в CI, что клиент актуален;
- контрактные тесты совместимых API на записанных запросах реальных клиентов;
- генератор синтетических данных (около 30 млн прослушиваний) и нагрузочный тест приёма — локально или на staging;
- продуктовые метрики: активация (первый скроббл за 24 часа), недельная аудитория, которая скробблит, удержание через 30 дней; плюс инструмент аналитики;
- пользовательские загрузки — с отдельного домена; CSRF-токены, несмотря на `SameSite=Lax`;
- копия бэкапов у второго провайдера в РФ;
- стрик не должен сгорать из-за поломки на нашей стороне: пока коннектор выключен kill switch'ем, дни автоматически замораживаются.

**Документация.** `architecture.md` весит около 360 КБ. Во всех документах около 64 пометок «не проверено», в [architecture.md](architecture.md), §16, — 47 открытых вопросов. Перед кодом стоит разделить их на блокирующие и неблокирующие и завести по ним issues. Крупные решения фиксировать короткими ADR.
