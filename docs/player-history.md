# Плеер: история прослушиваний и скробблинг — формат, база, сеть, синхронизация

> Статус: **решение на 24.10.2026, первая часть реализована** в [`player/core`](../player/core/README.md): запись истории, офлайн-очередь, отправка в Scrobb, привязка устройства и «сейчас играет». Синхронизация между устройствами, экспорт и другие сервисы — спроектированы, но не сделаны (§6–§8).
> Изменения: 24.10.2026 — привязка устройства (§5.2) и «сейчас играет» (§5.3).
> Опирается на серверную модель [architecture.md](architecture.md): §2.3 (`listens`), §5.1 (`ext_ids`), §5.4 (дедупликация), §18.3 (родной API), §18.7 (правило скроббла), §18.8 (офлайн-очередь), §18.9 (журнал отправленного). Общая архитектура плеера — [player-architecture.md](player-architecture.md).

## 0. Коротко

1. **База — SQLite**, отдельный файл `history.db` рядом с базой библиотеки, но не в ней. Библиотеку можно пересканировать, историю — нет.
2. **Каждое прослушивание — неизменяемая запись** со снимком метаданных и глобальным id (UUIDv7). Пишутся все прослушивания, включая пропуски; засчитанные по правилу §18.7 отмечаются флагом.
3. **Доставка — отдельная таблица по паре «прослушивание × сервис».** Это и офлайн-очередь (§18.8), и журнал «что отправлено» (§18.9). Новый сервис (ListenBrainz, Last.fm, будущие) — новое значение `target`, без миграции.
4. **Сеть — один фоновый поток ядра** через порт `HttpTransport` и sans-IO клиент `scrobb-client`: отправка очереди, привязка устройства по RFC 8628 и «сейчас играет». Сервер идемпотентен, поэтому повтор пачки безопасен.
5. **Синхронизация — объединение множеств по id.** Записи неизменяемы, id уникальны без координации, поэтому конфликтов нет. Засчитанные уже сходятся на сервере; полная история между устройствами требует нового эндпоинта (§6).
6. **Экспорт и импорт — JSON Lines в формате ListenBrainz**, свои поля — в `additional_info` (§7).

## 1. Три вида данных — три модели

| Данные | Природа | Модель |
|---|---|---|
| Прослушивания, все, включая пропуски | Неизменяемые факты | Журнал только на добавление, глобальный id |
| Доставка в сервисы | Короткоживущее изменяемое состояние | Очередь по паре «прослушивание × сервис» плюс журнал отправленного |
| Рейтинги, «любимые», плейлисты | Правки пользователя | Отдельная база `user.db`; синхронизация — «последняя запись побеждает» на гибридных логических часах (`scrobb-sync`), позже. Плейлисты уже хранятся так — [playlists.md](playlists.md) |

Смешивать их нельзя: у фактов нет конфликтов, у правок они есть, а очередь — служебная и чистится.

## 2. Где хранить

**SQLite** через `rusqlite` с флагом `bundled`: одна и та же версия SQLite на всех пяти ОС, на Android — без системной, к которой из NDK нет официального доступа.

- **Режим WAL**, `synchronous=NORMAL`: один писатель, параллельные читатели, запись не ждёт `fsync` на каждую транзакцию.
- **Таблицы `STRICT`**: SQLite проверяет типы колонок.
- **Версия схемы** хранится в `PRAGMA user_version`. Миграции — пронумерованные SQL-строки в коде, каждая в своей транзакции. Базу, созданную более новой версией приложения, ядро не открывает, чтобы не испортить.

**Отдельный файл `history.db`.** Библиотека — это кэш: её можно удалить и пересканировать. История невосполнима, поэтому её бэкапят, экспортируют и мигрируют отдельно. Пересборка библиотеки историю не трогает.

**Доступ — через трейт `HistoryStore`** в крейте `player-history`. Трейт без ввода-вывода, поэтому крейт собирается и под wasm.
- `SqliteHistory` (крейт `player-store-sqlite`, нативный ярус) — для приложений.
- `MemoryHistory` — для тестов и как образец поведения.
- Для веба позже — IndexedDB или SQLite-wasm на OPFS за тем же трейтом.

Оба хранилища проходят один набор проверок (`player-testkit`, модуль `history`), поэтому их поведение не расходится.

**Объём.** Около 300 байт на прослушивание; 50 прослушиваний в день — примерно 6 МБ в год. Храним всё и бессрочно: это основа «плеера с памятью» ([player-architecture.md](player-architecture.md) §1, требование 5).

**Время.** Только UTC, в миллисекундах. «По дням» считаем в таймзоне пользователя при запросе — как на сервере ([architecture.md](architecture.md), принцип «время — только UTC»).

## 3. Схема v1

```sql
CREATE TABLE meta (key TEXT PRIMARY KEY, value TEXT NOT NULL) STRICT;
-- device_id (UUID, создаётся при первом открытии); позже — курсоры синхронизации, кэш ScrobbleConfig+ETag

CREATE TABLE plays (
  id             TEXT PRIMARY KEY,   -- UUIDv7: уникален без координации, сортируется по времени; он же client_id
  started_at_ms  INTEGER NOT NULL,   -- начало, Unix UTC; listened_at = started_at_ms / 1000
  ended_at_ms    INTEGER,            -- NULL — ещё играет
  played_ms      INTEGER NOT NULL,   -- реально прозвучало: без пауз и перемоток вперёд
  outcome        TEXT NOT NULL CHECK (outcome IN
                   ('playing','finished','skipped','stopped','error','interrupted')),
  scrobbled      INTEGER NOT NULL DEFAULT 0,  -- пройден порог §18.7
  -- снимок метаданных на момент прослушивания: история не зависит от файлов и библиотеки
  title          TEXT NOT NULL,
  artists        TEXT NOT NULL,      -- JSON-массив; в API уходит через ", "
  album          TEXT,
  album_artist   TEXT,
  duration_ms    INTEGER,
  recording_mbid TEXT,
  ext_ids        TEXT,               -- JSON {"isrc": …, "yandex": …}: те же ключи, что ext_ids на сервере (§5.1)
  track_id       INTEGER,            -- TrackId библиотеки этого устройства; без внешнего ключа (другая база)
  device_id      TEXT NOT NULL,
  origin         TEXT NOT NULL DEFAULT 'player',  -- player | import:<формат> | remote (синхронизация)
  deleted_at_ms  INTEGER             -- надгробие: удалено пользователем (нужно синхронизации)
) STRICT;
CREATE INDEX plays_by_time  ON plays (started_at_ms);
CREATE INDEX plays_by_track ON plays (track_id, started_at_ms);

-- Офлайн-очередь (§18.8) и журнал «что отправлено» (§18.9), по сервисам.
CREATE TABLE deliveries (
  play_id       TEXT NOT NULL REFERENCES plays (id) ON DELETE CASCADE,
  target        TEXT NOT NULL,       -- scrobb; позже listenbrainz | lastfm | …
  state         TEXT NOT NULL CHECK (state IN ('pending','accepted','duplicate','rejected','expired')),
  reason        TEXT,                -- причина rejected от сервера
  updated_at_ms INTEGER NOT NULL,
  PRIMARY KEY (play_id, target)
) STRICT, WITHOUT ROWID;
CREATE INDEX deliveries_pending ON deliveries (target) WHERE state = 'pending';
```

Почему так:

- **Снимок метаданных, а не ссылка на библиотеку.** Файлы переименовывают, теги правят, библиотеку пересобирают. История должна показывать то, что звучало тогда. `track_id` оставлен только для быстрых локальных запросов («сколько раз я слушал этот трек»).
- **UUIDv7 как id.** Его создаёт устройство, без сервера. Он уникален глобально, поэтому истории разных устройств сливаются без перенумерации. Внутри одного устройства id растут в порядке создания, даже в пределах одной миллисекунды. Этот же id уходит в Scrobb как `client_id` (§18.3).
- **`played_ms`, а не `ended_at − started_at`.** Пауза и перемотка вперёд не считаются прослушанным временем (§18.7). Сервер повторно проверяет порог по `played_ms`.
- **Путь к файлу в историю не пишется.** История может уйти в экспорт или синхронизацию, а путь к файлу — это сведения о диске пользователя.
- **Токены — только в хранилище секретов ОС** (`SecureStore`, ключ `scrobb.device_token`), не в базе.
- **Состояние повторов отправки (backoff) — в памяти.** После перезапуска делается одна попытка сразу. Это проще и ничего не теряет: сама очередь — в базе.

## 4. Как ядро пишет прослушивания

Фасад ядра сообщает потоку истории только факты: «трек зазвучал», «пауза», «продолжение», «закончился так-то», «ошибка чтения». Время берётся из порта `Clock`: монотонное — для счётчика, Unix — для записи. Счётчик — общий для всех клиентов Scrobb `scrobb-rules::ListenTracker`.

| Что произошло | Что с записью |
|---|---|
| Трек зазвучал | Новая запись `playing`. Незакрытая предыдущая закрывается как `finished`: это переход без паузы |
| «Следующий», «предыдущий» на другой трек, новая очередь | Текущая закрывается как `skipped` в момент команды |
| Перемотка в начало («предыдущий» после 3 с, `Seek` в 0) | Текущая закрывается как `skipped`, начинается новая — повтор по §18.7 |
| «Стоп», конец очереди | `stopped` |
| Ошибка чтения звучащего трека | `error` |
| Трек доиграл до конца | `finished` |
| Пауза и продолжение | Счётчик стоит, затем снова идёт; на паузе — контрольная точка |
| Каждые 15 с звучания | Контрольная точка: сохраняется `played_ms` |
| Пройден порог скроббла | В одной транзакции: `scrobbled = 1` и строка `pending` в `deliveries`, если устройство привязано. Сразу попытка отправки |
| Запуск после падения | `playing` → `interrupted`, конец = начало + время на последней контрольной точке |
| Ядро закрывается | Открытая запись закрывается как `stopped` |

Пороги, контрольные точки и повторы отправки работают в одном цикле потока истории (`recv_timeout`). Любое изменение приходит сообщением, поэтому срок ожидания пересчитывается вовремя. Сеть блокирует только этот поток. Факты, пришедшие за это время, несут своё время и учитываются точно.

## 5. Сеть

### 5.1 Отправка засчитанного

Раз в 30 с и сразу после скроббла поток истории делает следующее:

1. Берёт до 50 записей `pending` (`MAX_LISTENS_PER_BATCH`, §18.3).
2. Собирает из снимков `ListenSubmission` с `client_id = plays.id` и `listened_at = started_at_ms / 1000`.
3. Строит запрос `ScrobbClient::submit_listens` и выполняет его через порт `HttpTransport`.
4. Раскладывает поштучные статусы в `deliveries` одной транзакцией.

Реакция на ответ — чистый автомат `scrobb_client::retry::Backoff`, общий для всех клиентов Scrobb:

| Ответ | Что делаем |
|---|---|
| Нет сети, `5xx`, непонятный ответ | Повтор через 30 с · 2ⁿ с разбросом, не дольше 1 ч |
| `429` | Ждём `Retry-After` |
| `401` | Отправка остановлена, очередь цела, событие «войдите заново». С тем же токеном не пробуем; новый токен в хранилище секретов снимает блокировку |
| `426` | Отправка остановлена до обновления, очередь цела |
| Поштучный `rejected` | `state = rejected` и `reason` — видно в журнале |
| `duplicate` | Считается доставленным |

- **Повтор безопасен.** Сервер вставляет прослушивание через `ON CONFLICT (user_id, played_at, alias_id) DO NOTHING` (§11.1), поэтому повтор пачки после таймаута даёт `duplicate`, а не дубль.
- **Лимиты очереди (§18.8).** Ждущие старше 14 дней и самые старые сверх 10 000 переходят в `expired` с предупреждением. Записи не удаляются: можно отправить вручную.
- **Нет привязки — нет очереди.** Если токена устройства нет, прослушивание пишется и отмечается засчитанным, но в очередь не ставится. Иначе у непривязанного плеера очередь копилась бы до `expired`. Предложить «отправить последние 14 дней» после привязки — позже.
- **Для интерфейса.** Событие `Event::Scrobbling { pending, state }` — для «в очереди N», «войдите заново» (§18.2). Лента истории — `Core::recent_plays(before_ms, limit)`, страницами от новых к старым.

### 5.2 Привязка устройства

Плеер не видит ни паролей, ни кодов из SMS: он привязывается к сессии на сайте по OAuth 2.0 Device Authorization Grant ([RFC 8628](https://www.rfc-editor.org/rfc/rfc8628), [architecture.md](architecture.md) §18.4).

1. Оболочка шлёт `Command::LinkScrobbAccount { device_name }`. Ядро вызывает `POST /api/v1/devices/authorize` с `client_kind = player`, платформой и версией.
2. Ядро присылает `Event::ScrobbLinkCode { user_code, verification_uri_complete }`. Оболочка показывает код и открывает страницу системным браузером. Состояние — `Linking`.
3. Ядро опрашивает `POST /api/v1/devices/token` не чаще `interval`.
   - `authorization_pending` — ждём дальше.
   - `slow_down` — интервал растёт на 5 с.
   - Сбой сети или сервера — пробуем дальше, пока код жив.
4. Чем кончается привязка:
   - **подтверждено** — токен `scr_…` ложится только в хранилище секретов ОС (ключ `scrobb.device_token`), состояние `Ready`; сразу уходят «сейчас играет» и очередь;
   - **отказ на сайте, истёкший код** (проверяется и локально по `expires_in`) или **устаревшая версия** — ошибка с понятным текстом, состояние `NotLinked`.
5. `Command::CancelScrobbLink` прекращает опрос: пользователь закрыл окно с кодом.

**Отвязка — `Command::UnlinkScrobbAccount`.** Ядро снимает «сейчас играет», пока токен ещё действует, затем отзывает токен (`DELETE /api/v1/devices/current`) и удаляет его локально.
- Если сервер не ответил, токен всё равно удаляется, а пользователь получает подсказку отозвать устройство в «Приложениях» на сайте.
- История и очередь остаются; очередь уйдёт после следующей привязки.

### 5.3 «Сейчас играет»

Политика — общий `scrobb-rules::NowPlayingGate` ([architecture.md](architecture.md) §18.7).

| Что произошло | Запрос |
|---|---|
| Трек зазвучал, в том числе следующий | `POST /api/v1/scrobble/now-playing` с позицией 0. Следующий трек заменяет предыдущий без сброса между ними |
| Продолжение после паузы | `POST` с текущей позицией |
| Перемотка | `POST` с новой позицией, но не чаще раза в минуту |
| Пауза | Ничего. Пауза дольше 5 минут — `DELETE` |
| «Стоп», конец очереди, закрытие ядра | `DELETE` |
| Привязка только что завершилась, трек звучит | `POST` сразу |

Сроки считаются по времени самих фактов, а не по моменту обработки, поэтому задержка потока на сетевом запросе их не сдвигает. «Сейчас играет» не повторяется при ошибках: через минуту оно уже неважно. Но ответы `401` и `426` останавливают все запросы так же, как при отправке очереди. Без привязки запросов нет.

При закрытии ядра `DELETE` уходит синхронно, поэтому таймаут запросов в адаптере `HttpTransport` должен быть коротким (несколько секунд).

## 6. Синхронизация (спроектировано, не сделано)

Схема готова к синхронизации без миграции: id глобально уникальны, записи неизменяемы, удаление — надгробие, у каждой записи есть `device_id` и `origin`. Поэтому слияние историй двух устройств — объединение множеств по `id`, конфликтов нет.

1. **Засчитанные — уже через сервер.** Со всех устройств и клиентов они попадают в `listens`; сервер — источник истины для статистики аккаунта. Отдельно синхронизировать их не нужно.
2. **Чужие скробблы на устройстве** (например, на телефоне видно, что слушал на компьютере). Забираем `GET /api/v1/users/{u}/recent?before=` (§9.3), кладём с `origin = 'remote'`, с библиотекой сопоставляем по MBID или `match_key`.
   - Свои записи нужно узнавать, чтобы не задвоить. Сейчас сервер `client_id` не хранит. **Предложение бэкенду:** класть `client_id` в `listens.additional_info` рядом с `source` — это дёшево.
   - Без этого остаётся сравнение по `(listened_at, match_key)` — после контракта `contracts/match-key`.
3. **Полная история с пропусками между устройствами.** Нужен новый эндпоинт `/api/v1/sync/plays`: отправка и получение по серверному курсору, множество только на рост, надгробия. Это решение бэкенда и вопрос приватности: пропуски — более личные данные, чем скробблы. Отложено.
4. **Рейтинги, «любимые», плейлисты.** Таблицы `sync_ops` и `sync_state` в `user.db` на `scrobb-sync::{Lww, Hlc}`; «любимые» соответствуют серверным `favorites`. Нужны эндпоинты; общий с сервером `match_key` уже есть — [`contracts/match-key/v1.json`](../contracts/match-key/v1.json). Как синхронизировать плейлисты и что нужно от сервера — [playlists.md](playlists.md) §7–§8.

## 7. Будущие сервисы и форматы

- **Другой сервис скробблинга — это значение `deliveries.target` и адаптер** «собрать запрос / разобрать ответ» в стиле sans-IO. Схема не меняется, токены — в `SecureStore` по ключу `target:<id>`.
  - ListenBrainz: `POST /1/submit-listens` с токеном пользователя.
  - Last.fm: `track.scrobble`, до 50 в запросе, с подписью `api_sig`.
  - **По умолчанию сервис один — Scrobb.** Пересылать дальше разумнее с сервера, чем из каждого клиента.
  - Если пользователь всё же шлёт и в Scrobb, и в Last.fm, а потом импортирует Last.fm, дубль снимет дедупликация ±90 с (§5.4). `listened_at` у обеих копий одинаковый.
- **Новые идентификаторы** (Яндекс Музыка, VK, Звук, ISRC) ложатся в `ext_ids` с теми же ключами, что `external_ids` на сервере (§5.3). По ним сервер склеивает один трек из разных источников.
- **Экспорт и импорт — JSON Lines в формате ListenBrainz**, одно прослушивание на строку:

  ```json
  {"listened_at": 1760000000, "track_metadata": {"artist_name": "Кино", "track_name": "Кукушка", "release_name": "Чёрный альбом", "additional_info": {"duration_ms": 400000, "recording_mbid": "…", "submission_client": "Scrobb Player", "scrobb_play_id": "0192…", "played_ms": 212000, "outcome": "finished"}}}
  ```

  - Режим «только засчитанные» понимают ListenBrainz и импорт Scrobb.
  - Режим «вся история» включает пропуски — для резервной копии и переноса между устройствами.
- **Импорт из других плееров.** Прослушивания со временем пишутся с `origin = 'import:<формат>'`. Счётчики без времени (foo_enhanced_playcount, iTunes) — отдельной таблицей позже; в стриках они не участвуют.

## 8. Что сделано и что дальше

**Сделано** ([`player/core`](../player/core/README.md), раздел «История и скробблинг»):
- модель и трейт в `player-history`;
- SQLite-хранилище `player-store-sqlite` со схемой v1;
- автомат повторов `scrobb_client::retry::Backoff`;
- поток истории в `player-core`: запись, контрольные точки, восстановление после падения, очередь и отправка в Scrobb;
- привязка и отвязка устройства по RFC 8628 и «сейчас играет» (§5.2–§5.3);
- общие проверки хранилищ и тесты фасада с подделанными сервером и часами.

**Дальше, по порядку:**
1. кэш `GET /api/v1/scrobble/config` (пороги, размер пачки, `ETag`, отключённые коннекторы);
2. после привязки — предложить отправить засчитанное за последние 14 дней, которое не ушло без токена;
3. локальная статистика и стрики поверх `plays`;
4. экспорт и импорт JSON Lines;
5. синхронизация (§6, уровни 2–4) — после решений на бэкенде;
6. хранилище для веба.
