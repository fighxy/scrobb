# Ядро плеера Scrobb (каркас)

> Статус: **каркас**. Решение «свой плеер сейчас не писать» остаётся в силе ([local-players-research.md](../../docs/local-players-research.md) §6.5). Каркас закрепляет архитектуру из [player-architecture.md](../../docs/player-architecture.md) и выделяет код, общий со Scrobb: протокол, правило скроббла, синхронизацию.

## Структура

```

  crates/
    scrobb-api/              DTO родного API Scrobb (§18.3, §18.4)            ─┐
    scrobb-rules/            правило скроббла и «сейчас играет» (§18.7)         │ ярус Scrobb:
    scrobb-client/           клиент API без ввода-вывода (sans-IO), повторы     │ собирается под wasm32

    player-domain/           треки, состояние, окна списков                    ─┐ общий ярус плеера:
    player-playback/         очередь, повтор, взгляд вперёд                     │ собирается под wasm32
    player-history/          история: модель, трейт хранилища, скробблы        ─┘
    player-ports/            порты: звук, медиасессия, файлы, секреты, сеть, часы ─┐
    player-engine/           звуковой движок: gapless, ReplayGain, перемотка      │ нативный

    player-plugins/          хост WASM-плагинов (заготовка)                       │
    player-core/             фасад: очередь + библиотека + движок + история      ─┘
    player-testkit/          обвязка тестов: ручной вывод звука, часы, фикстуры,
```

## Ярусы

| Ярус | Крейты | Кто использует | Ограничения |
|---|---|---|---|
| **Scrobb** | `scrobb-api`, `scrobb-rules`, `scrobb-client`, `scrobb-sync` | Плеер; десктоп-клиент Scrobb на Tauri (тоже Rust, [architecture.md](../../docs/architecture.md) §18.12); веб-приложение и расширение через `bindings/wasm` | Без ввода-вывода, системного времени и потоков; собирается под `wasm32-unknown-unknown`; не зависит от `player-*` |
| **Плеер, общий** | `player-domain`, `player-playback`, `player-history` | Ядро плеера; при желании — веб (например, веб-плеер на сайте) | Те же, что у яруса Scrobb |
| **Плеер, нативный** | `player-ports`, `player-engine`, `player-output-cpal`, `player-library`, `player-store-sqlite`, `player-metadata`, `player-plugins`, `player-core` | Только плеер | Всё платформенное — только через порты |
| **Привязки** | `bindings/ffi`, `bindings/wasm` | Оболочки на SwiftUI и Compose; веб и расширение | Наружу — только фасад `player-core` (ffi) и ярус Scrobb (wasm) |

## Правила зависимостей

1. `scrobb-*` не зависят от `player-*`: ярус Scrobb можно забрать в десктоп-клиент или в веб без плеера.
2. Внизу — `scrobb-api`, контракт с бэкендом. Сейчас DTO написаны вручную по [architecture.md](../../docs/architecture.md) §18.3–§18.4; позже они генерируются из OpenAPI бэкенда.
3. Модули плеера не зависят друг от друга «по горизонтали». Общее — только `player-domain` и `player-ports`; связывает модули только `player-core`.
4. Время, сеть, файлы и секреты — только через порты (`player-ports`) или в стиле sans-IO: `scrobb-client` строит запросы, а выполняет их вызывающий код.
5. Список крейтов, обязанных собираться под wasm32, — в `scripts/check.sh` (`WEB_SAFE`); проверка падает, если в них появится несовместимая зависимость.

## Связь с веб-приложением Scrobb

- **Протокол — один на все клиенты.** DTO родного API лежат в `scrobb-api`, а `scrobb-client` строит и разбирает запросы, не выполняя их. Поэтому один код работает в плеере (порт `HttpTransport`), в Tauri-клиенте и в браузере (`fetch`).
- **Правило скроббла проверяется по одним векторам.** `scrobb-rules` прогоняется по [`contracts/scrobble-rules/v1.json`](../../contracts/scrobble-rules/v1.json). Эти же векторы должны проходить бэкенд (повторная проверка, §11.1, шаг 6) и TypeScript-код расширения.
- **Синхронизация.** `scrobb-sync` описывает рейтинги и «любимые», которые веб-приложение будет показывать и править. Для этого нужны эндпоинты синхронизации на сервере и общая с бэкендом нормализация ключа трека (`contracts/`, `match-key` — план).
- **Что нужно от бэкенда, когда плеер появится:**
  - новое значение `player` в `source.kind` и `client_kind` (сейчас только `extension` и `desktop`, §18.3);
  - эндпоинты синхронизации;
  - OpenAPI, из которого генерируются DTO.
- **Открытый вопрос:** [architecture.md](../../docs/architecture.md) §18.12 планирует `scrobbler-core` на TypeScript. Каркас показывает альтернативу — правило и протокол на Rust с поставкой в веб через wasm. Решать вместе с выбором стека десктоп-клиента (§16, п. 42).

## Сборка и проверки

```sh
cd player/core
scripts/check.sh
```

Нужен Rust 1.89+ (edition 2024; столько требуют текущие `rusqlite` и `uuid`). Для встроенной SQLite нужен компилятор C. Для проверки под wasm: `rustup target add wasm32-unknown-unknown`; без этой цели шаг пропускается с предупреждением.

## Звуковой движок

`player-engine` — первая рабочая часть ядра.

- **Декодирование** — Symphonia 0.6: MP3, AAC, FLAC, ALAC, Vorbis, WAV, AIFF, ADPCM в контейнерах MP4, MKV, Ogg, CAF. Opus в Symphonia пока нет.
- **Gapless:** задержку и паддинг кодера Symphonia обрезает сама — для FLAC, MP3 с заголовком LAME, Vorbis, ALAC, WAV. Для AAC в MP4 обрезки пока нет (ограничение Symphonia).
- **Рабочий поток** декодирует вперёд на `buffer_ms` и заранее открывает следующий трек.
- **Ресемплинг** — rubato, синхронный FFT-ресемплер; работает в рабочем потоке, а не в аудиопотоке. Отклонение от исходного сигнала после пересчёта 44,1 → 48 кГц — около 2·10⁻⁵, на уровне погрешности самого 16-битного файла. Задержка фильтра обрезается, а хвост в конце трека дописывается, поэтому длина выхода ровно `ceil(кадры × новая частота / старая)`. Треки одной частоты проходят через один непрерывный ресемплер, и стык между ними неотличим от середины файла. Частоту вывода задаёт `EngineConfig::output_rate`:
  - `FollowTrack` (по умолчанию, для десктопа) — частота трека, если устройство её поддерживает (звук без пересчёта), иначе частота устройства с ресемплингом. Трек с другой частотой переоткрывает вывод, и переход не бесшовный;
  - `Fixed(48000)` (для телефонов) — всё приводится к одной частоте, переходы бесшовные при любых частотах треков.
- **Аудиопоток** читает два lock-free кольцевых буфера (rtrb) и атомики: без блокировок, выделения памяти и ввода-вывода. Перемотка и смена трека отбрасывают старые данные по номеру поколения.
- **Пауза, продолжение и громкость** меняются плавно, за 5 мс; после перемотки — плавное нарастание. На паузе буфер не тратится.
- **ReplayGain** — по треку или альбому, с предусилением и защитой от клиппинга по пику.
- **Следующие треки** передаются списком (`Engine::set_upcoming`), привязанным к треку, за которым они идут. Сломанный трек движок перешагивает сам, без обращения к фасаду. Список, опоздавший к ушедшему вперёд движку, отбрасывается.
- **События** приходят с эпохой (`EngineMessage`): она растёт при каждом `play` и `stop`, и события отменённого можно отбросить. Виды событий: `TrackStarted` (с флагом `gapless`), `Preloading` («пора передать следующие треки»), `Seeked` (перемотка выполнена, точная позиция), `Finished`, `Error`. Позиция — `Engine::playhead()`.

Что проверяют тесты (`crates/player-engine/tests`; фикстуры лежат в `crates/player-testkit/fixtures`, их генерирует `generate.sh` через ffmpeg):
- два куска FLAC, разрезанные посреди пакета, склеиваются в исходный сигнал сэмпл в сэмпл;
- FLAC со встроенной обложкой (блок PICTURE) звучит так же, как без неё;
- два куска MP3 дают ровно исходное число кадров и совпадают с декодированием ffmpeg;
- перемотка попадает в точный кадр (тест ждёт события `Seeked`, поэтому не зависит от тайминга потоков);
- на паузе ни один кадр не теряется и не повторяется;
- трек с другой частотой переоткрывает вывод;
- следующий трек, переданный с опозданием, подхватывается без паузы;
- маленький буфер не вешает движок;
- ресемплинг: точная длина, сохранение высоты тона и фазы в обе стороны, независимость от размера кусков; две половины файла после ресемплинга совпадают с ресемплингом целого файла бит в бит; с фиксированной частотой 44,1 и 48 кГц стыкуются без переоткрытия вывода; перемотка с ресемплингом попадает во время.

Послушать на своём компьютере (вывод — устройство по умолчанию, на Linux нужен `libasound2-dev`):

```sh
cd player/core
cargo run --release -p player-output-cpal --example play -- a.flac b.flac c.mp3
# одна частота для всех треков:
cargo run --release -p player-output-cpal --example play -- --rate=48000 a.flac b.flac
```

Чего пока нет: кроссфейда, даунмикса многоканального звука, эквалайзера, bit-perfect и монопольного режима, Opus.

## Фасад

`player-core` связывает очередь, библиотеку и движок; оболочки работают только с ним.

- **Команды:** `PlayQueue`, `Pause`, `Resume`, `Stop`, `Next`, `Previous`, `Seek`, `SetRepeat`, `SetVolume`; для Scrobb — `LinkScrobbAccount`, `CancelScrobbLink`, `UnlinkScrobbAccount` (раздел «История и скробблинг»).
  - «Назад» в первые 3 секунды трека включает предыдущий трек, позже — начало текущего.
  - «Дальше» в конце очереди останавливается на последнем треке.
  - «Играть» после остановки начинает текущий трек очереди сначала.
- **Очередь хранит идентификаторы**, а файл берётся из библиотеки (`TrackStore`). Пока библиотека живёт в памяти (`MemoryLibrary`); когда появятся сканер и база, на её место встанет SQLite.
- **Движку передаются 3 следующих трека.** Если при бесшовном переходе движок ушёл вперёд сам, очередь его догоняет.
- **Треки без файла и вне библиотеки пропускаются.** Если такой трек стоит между двумя другими, переход всё равно остаётся без паузы. Не больше 10 пропусков подряд.
- **Состояние** (`PlayerState`) приходит наблюдателю после каждого изменения. Наблюдатель и медиасессия вызываются без удержания блокировок, поэтому из колбэка можно сразу отправлять команды.
- **События движка** обрабатывает отдельный поток. События отменённого (по эпохе) отбрасываются: запоздавшее «трек начался» не сдвинет очередь после «Назад» и не включит «играет» после «Стопа».

Тесты (`crates/player-core/tests`) проходят весь путь от команды до звука:
- очередь играет без пауз сэмпл в сэмпл;
- работают «Дальше», «Назад», «Стоп», «Играть», пауза, перемотка, громкость и повтор трека;
- сломанные треки перешагиваются;
- команду можно отправить из колбэка.

Отдельный тест с задержанным потоком событий детерминированно воспроизводит запоздавшее событие. Без фильтра по эпохам он падает. Стабильность проверена 240 параллельными прогонами.

Пока не подключены: медиасессии ОС (порт есть, адаптеров нет).

## История и скробблинг

Формат, база, синхронизация и будущие сервисы — в [player-history.md](../../docs/player-history.md). Коротко:

- **Хранилище — SQLite**, отдельный файл `history.db` (`player-store-sqlite`): режим WAL, таблицы `STRICT`, миграции по `PRAGMA user_version`. Ядро видит его через трейт `HistoryStore` из `player-history`. Для тестов есть `MemoryHistory`; оба хранилища проходят одни и те же проверки из `player-testkit`.
- **Запись — каждое прослушивание**, включая пропуски. В записи есть:
  - id — UUIDv7, он же `client_id` при отправке;
  - снимок метаданных;
  - реальное время звучания (без пауз и перемоток);
  - исход: `finished`, `skipped`, `stopped`, `error`, `interrupted`;
  - флаг «засчитано».
- **Поток истории** (`player-core-history`) получает от фасада факты и сам ведёт счётчик `scrobb-rules::ListenTracker`.
  - Каждые 15 с звучания сохраняет контрольную точку.
  - После падения закрывает незакрытые записи как `interrupted`.
  - Засчитанное сразу ставит в очередь и отправляет пачками до 50, через порт `HttpTransport` и `scrobb-client`.
  - Повторы — `scrobb_client::retry::Backoff`: 30 с – 1 ч, `Retry-After`; `401` и `426` останавливают отправку без потери очереди.
  - Лимиты очереди — 14 дней и 10 000 записей.
- **Связь со Scrobb включается**, когда в `CoreConfig::scrobb` задан сервер, есть порты сети и секретов и хранилище истории. Без этого команды привязки отвечают `MissingPort` или `NotConfigured`.
- **Привязка устройства** — RFC 8628:
  - `LinkScrobbAccount { device_name }` → событие `ScrobbLinkCode { user_code, verification_uri_complete }`; оболочка показывает код и открывает страницу системным браузером;
  - ядро опрашивает сервер не чаще `interval`, на `slow_down` — реже;
  - подтверждено — токен ложится в `SecureStore` (`SCROBB_TOKEN_KEY`); отказ или истёкший код — ошибка с понятным текстом;
  - `CancelScrobbLink` прекращает опрос, `UnlinkScrobbAccount` отзывает токен на сервере и удаляет его.
  - Без токена история пишется, но в очередь ничего не ставится.
- **«Сейчас играет»** — по `scrobb-rules::NowPlayingGate`: при старте трека и после паузы, при перемотке не чаще раза в минуту, сброс на «Стопе», при закрытии ядра и после паузы дольше 5 минут.
- **Оболочке:** событие `Event::Scrobbling { pending, state }` — состояния `NotLinked`, `Linking`, `Ready`, `Retrying`, `Unauthorized`, `UpgradeRequired` («в очереди N», «войдите заново») — и лента `Core::recent_plays(before_ms, limit)`.

Тесты (`crates/player-core/tests/scrobb.rs`) идут с подделанным сервером Scrobb и часами, которые двигает тест. Чтобы таймеры потока истории не ждали реального времени, порт `Clock` сообщает, сколько ждать на самом деле (`real_wait`): настоящие часы — столько же, `ManualClock` — не больше 2 мс. Проверяется:
- история: исходы и время звучания при «Дальше», бесшовном переходе и «Стопе»; пауза не считается, перемотка в начало — новое прослушивание; восстановление после падения;
- отправка: сразу после порога с id записи; `401` с сохранением очереди до новой привязки; повтор после ошибки сети; непривязанное устройство не копит очередь;
- привязка: код и запрос с типом клиента, опрос не чаще интервала, сохранение токена и отправка с ним; `slow_down` и отказ; истёкший код и отмена; отвязка с отзывом токена;
- «сейчас играет»: пауза, сброс после 5 минут, продолжение, ограничение перемотки, «Стоп», смена трека без сброса, закрытие ядра.

Проверено, что тесты ловят ошибки: каждая из 15 внесённых поломок (6 — в истории и отправке, 9 — в привязке и «сейчас играет») роняет хотя бы один тест.

## Оболочки

- **Десктоп** — [`player/shells/desktop`](../shells/desktop/README.md): Tauri 3 + React. Ядро подключено крейтом, без FFI; типы ядра для этого сериализуются (`serde`), формат закреплён тестом `crates/player-core/tests/json.rs`.
- **Что ядро даёт оболочкам сверх команд и событий:**
  - `Core::queue()` — треки очереди по порядку для «Далее». Отдельно от снимка состояния: очередь бывает длиной во всю библиотеку, а снимок уходит в окно при каждой смене состояния.
  - `player-library::covers` — обложка трека через порт `FileAccess`: встроенная в теги (сначала «передняя обложка»), иначе `cover`/`folder`/`front`/`album`/`albumart` с расширением `.jpg`/`.jpeg`/`.png` в папке трека. Уменьшение и кэш — дело оболочки.
  - При сканировании теги читаются без картинок (`read_cover_art(false)`): обложка в FLAC бывает на мегабайты.
